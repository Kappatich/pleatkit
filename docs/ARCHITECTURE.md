# Pleatkit: архитектура демо

Имя: **pleatkit** (npm scope `@pleatkit/*`; до 2026-10-18 morphkit, решение 68). Либа, которая позволяет агенту внутри веб-приложения переписывать разрешённые части интерфейса в рантайме, с коммитом, откатом и персональными версиями на пользователя.

Решения приняты 2026-10-17: архитектура здесь (Fable 5.1), код пишет Opus 5.5 high. Локальные модели не используем. Провайдер модели по умолчанию Anthropic через ключ клиента (BYOK), провайдер сменный.

Контекст и обоснование решений ведутся во внутреннем журнале решений (приватный репозиторий).

---

## 1. Принципы

1. **Три зоны в проекте клиента.** `core` компилируется и минифицируется, агент видит только `.d.ts`. `readonly` агент читает как исходник, но не правит. `dynamic` агент правит, и именно эта папка собирается в рантайме. Зоны задаются в конфиге плагина Vite по глобам.
2. **Снимок, а не патч.** Состояние динамической зоны пользователя это полный снимок файлов (`Snapshot`). Версии это цепочка снимков. Undo это переход к родительскому снимку. Никаких diff-форматов в MVP.
3. **Черновик → коммит.** Агент пишет в черновик (`draft`). Приложение не меняется, пока не вызван `commit`. Коммит компилирует весь `dynamic` целиком; если ошибка, коммит отклонён, агент получает текст ошибки. Это пункт 7 спеки.
4. **Подмена без перезагрузки.** Каждый файл динамической зоны экспортирует React-компоненты. Приложение обращается к ним через `<Dynamic id="customer-card" />`, а не через import. Рантайм держит реестр `id → текущий модуль` и перерисовывает при коммите.
5. **Ключ модели никогда не в браузере.** Агент работает на сервере клиента (`@pleatkit/agent`, Node). Браузер общается с ним по HTTP/SSE.
6. **Хранилище сменное.** Интерфейс `SnapshotStore` с двумя реализациями: `LocalStore` (IndexedDB, для демо и десктопа) и `HttpStore` (наш сервер, Postgres). Выбор в конфиге рантайма.
7. **Песочница по уровням.** В MVP правки пользователя выполняются в том же окне (угроза только себе). Режим `isolated: true` рендерит динамические компоненты в iframe с `sandbox="allow-scripts"` и CSP. Делаем как флаг, в демо показываем оба.

## 3. `@pleatkit/vite-plugin`

```ts
// vite.config.ts у клиента
import pleatkit from '@pleatkit/vite-plugin'
export default defineConfig({
  plugins: [react(), pleatkit({
    zones: {
      dynamic:  ['src/dynamic/**'],
      readonly: ['src/readonly/**', 'src/components/ui/**'],
      // всё остальное = core
    },
    externals: ['react', 'react-dom', 'react/jsx-runtime', '@/components/ui/*', '@/lib/utils'],
  })]
})
```

Что делает:
1. На сборке и в dev собирает **манифест** `pleatkit.manifest.json`:
   - `dynamic`: `{ path, source }` для каждого файла (исходник TSX как есть), это **базовый снимок** (`baseSnapshot`), версия 0 для каждого нового пользователя;
   - `readonly`: `{ path, source }` исходники для чтения агентом;
   - `coreTypes`: `.d.ts` для `core`, сгенерированные `tsc --declaration --emitDeclarationOnly` (в демо можно ограничиться `.d.ts` для файлов, которые `dynamic` импортирует);
   - `externals`: список имён, которые рантайм подставит из реестра.
2. Виртуальный модуль `virtual:pleatkit/manifest` импортирует манифест в приложение.
3. Виртуальный модуль `virtual:pleatkit/externals` генерирует реестр: `{ 'react': React, '@/components/ui/button': () => import('...') ... }`. Externals с `*` раскрываются по файловой системе на этапе сборки.
4. Файлы из `dynamic` в основной бандл **тоже попадают** как fallback (чтобы приложение работало до первой правки и чтобы SSR/первая отрисовка не ждали esbuild-wasm). Рантайм на старте использует fallback, если у пользователя нет снимков.

### 4.2. Компиляция и `check`

- Режим по умолчанию `server` (DECISIONS 22): агент компилирует нативным esbuild, подписывает ed25519 и кладёт в store-server; браузер грузит `/pleatkit/b/<app>/<key>.js` через `<script integrity>` + `import()`. Режим `browser`: esbuild-wasm в странице, при ошибке wasm сам уходит на `server`.
- **Один `check` для браузера и сервера** (`Compiler.compile` в `@pleatkit/runtime/compiler`, code review 06 п. 12): сборка virtual-fs с externals, затем статические правила, защищённые элементы и правило default export по одному AST (esbuild `transform` снимает TypeScript, acorn + acorn-jsx разбирают, позиции возвращаются по source map). В браузере модуль правил грузится лениво, только в режиме `browser`.
- Ключ бандла: версия компилятора, формат, namespace, CSS-режим, `contextHash` (readonly, externals, alias, корни зон, хеш темы Tailwind) и хеш файлов. `baseHash` снимка считается из тех же частей, поэтому релиз с новым readonly API или темой делает снимки устаревшими, и они переносятся сами (B5).
- CSS правок: `.css` зоны оборачивается в `@scope ([data-pleatkit-id])` при компиляции, весь CSS правок кладётся в `@layer pleatkit-edits` (несвязанный CSS хоста всегда сильнее). Слой правок объявлен после слоёв хоста и потому сильнее их; у Tailwind 4 утилиты хоста тоже в `@layer utilities`, и вторая копия утилиты, которая у хоста уже есть (`.hidden`), перебивала его варианты на элементах вне правок (`hidden md:block` сайдбара shadcn-admin: после каждого коммита сайдбар пропадал; нашёл визуальный судья, блок 4). Поэтому `applyCss` выбрасывает из CSS правок правила, все классы селектора которых уже стилизованы таблицами страницы (`withoutStyledRules` + `pageStyledClasses` в `css-scope.ts`: обход `document.styleSheets` без собственного `<style data-pleatkit-css>`, чужие по CORS таблицы пропускаются); такие утилиты остаются за хостом в порядке Tailwind, правка добавляет только новые. UI pleatkit рендерится в shadow root (`PleatkitUiRoot`), поэтому CSS правки не может его спрятать.
- Этап 5, блок 5 (найдено слепыми установками). **CSS-модули зоны** (`*.module.css`) собираются загрузчиком esbuild `local-css` (`loaderFor` в `vfs.ts`): импорт даёт карту локальных имён, как у Vite; раньше загрузчик `css` давал `{}`, и после любой правки все панели с CSS-модулями теряли классы. **Собственный CSS зоны не в слое**: блоки `@scope ([data-pleatkit-id])` (её `.css` и CSS-модули) `layeredCss` оставляет вне `@layer pleatkit-edits`, как они и стоят в релизе; в слое несвязанный сброс хоста (`* { margin: 0 }`) их перебивал. В слое остаются утилиты Tailwind правок.
- **Правка не накрывает страницу** (решение 82.4). Статическое правило `no-portal`: `createPortal` (именованный, переименованный, через пространство имён) и вставка узлов в `document.body`/`documentElement`/`head` (`appendChild`, `append`, `prepend`, `insertBefore`, `replaceChildren`, `insertAdjacentElement`, …) отклоняются: всё, что рендерит правка, остаётся в поддереве её панели. Рантайм (`z-cap.ts` + `contain.ts`, `watchEditedPanel` в `<Dynamic>`, только пока панель показывает правку) прижимает `z-index` позиционированных элементов панели к `EDIT_Z_INDEX_CAP` = 999 (ниже оверлеев UI-китов хоста от 1000 и далеко ниже лаунчера pleatkit 2147482000) и следит за изменениями `style`/`class` через `MutationObserver`; исходное значение остаётся в `data-pleatkit-zcap`. **Правка заперта в рамке своей панели** (решение 84.4, `contain.ts`): обёртка остаётся `display: contents` (дети панели — те же элементы сетки/flex хоста), а корневые элементы панели (дети обёртки сквозь вложенные `display: contents`) получают `contain: paint !important`: каждый становится содержащим блоком для своих `fixed`/`absolute` потомков и обрезает всё внутри по своей рамке; место в раскладке хоста не меняется. Корень, который сам `fixed` (привязан к окну, рамка панели его не удержит при прокрутке) или `absolute` и выходит за элемент хоста, держащий панель, становится `position: static`. `fixed`/`absolute` элемент вне любой paint-containment панели (корень, к которому она неприменима: строка таблицы, inline `<span>`) запирается через ближайшего предка в панели, который её принимает (ячейка), иначе становится `static`. Метки: `data-pleatkit-clip` на элементах с нашей `contain: paint`, `data-pleatkit-contained="clip|static"` на позиционированных элементах, вышедших за рамку панели. Цена: выпадающее меню или подсказка внутри правленой панели обрезаются по её краю (оверлеи UI-кита хоста через портал не затронуты), корень панели — свой контекст наложения и блочного форматирования (поля первого/последнего потомка не схлопываются сквозь него). Красная команда: `rt-r-zindex-overlay` (проверка `launcherOnTop`) и `rt-r-fixed-fullscreen` (полноэкранный `fixed` с z-index 998 и `absolute` со смещением −5000 px; проверка `containedInPanel`: каждый `fixed`/`absolute` элемент панели рисуется внутри её рамки, ориентиры хоста (`header`, `nav`, `aside`) не закрыты и получают клик в своём центре).
- Без `crypto.subtle` (http не на localhost) хеши считаются на JS; подпись бандлов проверить нельзя, и с `publicKey` правки отклоняются (doctor `secure-context`).
- Inline source map только в dev-сборке (`virtual:pleatkit` `dev`).

- **URL из данных** (решение 74.3): статическое правило пропускает вычисленный URL в `src`, `href`, `poster`, `action`, `formAction` обычного элемента (тег со строчной буквы), если он не начинается с записанного в коде абсолютного адреса или `javascript:`; решает рантайм. Реестр externals (`loader.ts`) отдаёт бандлам правок `react/jsx-runtime`, `react` и `react-dom` через `guardModule` (`url-guard.ts`): `jsx`/`jsxs`/`jsxDEV`, `createElement`, `cloneElement` убирают у создаваемого строкового элемента URL-пропсы, которые по разбору WHATWG URL против `document.baseURI` уходят с origin страницы (схема не http(s), другой хост или порт, `//host`, `/\host`, `user@host`, `javascript:`, `data:`), а также `dangerouslySetInnerHTML`, `srcDoc` и `url()` других хостов в `style`; `mailto:`/`tel:` остаются в `href`; списки (`srcSet`, `ping`) остаются, только если все адреса свои; ресурсные подсказки `react-dom` (`preinit`, `preload`, …) работают только для своего origin. При непрозрачном origin страницы не остаётся ни один URL своего origin (абсолютный URL на хост из `allowedHosts` остаётся). Компоненты (не строковый тип) не трогаются: их URL-пропсы из данных по-прежнему отклоняет статическое правило.
- **Внешние хосты `allowedHosts`** (решение 63.1): опция vite-plugin, точные имена хостов (приводятся к нижнему регистру, IDN к punycode; схема, путь, порт, user info, `%`, `*`, IP-адрес, хвостовая точка и имя без точки отклоняются при сборке; поддомены перечисляются по одному). Список пишется в серверный манифест и в его браузерную копию (`virtual:pleatkit/manifest`, а для изолированной рамки в `startIsolatedHost`). Рантайм-охрана (`allowedHostUrl` в `url-guard.ts`, список приходит через `installExternals(…, { allowedHosts })`) оставляет URL на чужом хосте только в `<img src>`, `<img srcSet>` и `<a href>`: схема `https:`, порт по умолчанию, без user info, `hostname` после разбора WHATWG URL есть в списке; значение заменяется каноническим `url.href` (верхний регистр, `\`, табуляции, `%2E` в хосте читаются так же, как их прочтёт браузер; `//host` проходит только на https-странице). `srcSet` проверяется в двух разборах (по запятым и как его читает HTML-парсер), каждый адрес обоих должен пройти. Всё остальное остаётся только на своём origin: `poster`, `action`, `formAction`, `ping`, `xlinkHref`, `url()` в `style`, `<video>`, `<source>`, `<iframe>`, `<script>`, `<link>`, ресурсные подсказки `react-dom`, `http:`. Статическое правило (`check.ts`) пропускает записанный в коде `https://<хост>` с `/` или концом строки после хоста в `<img src>` и `<a href>`, если хост буквально (строчными, без порта, экранирования и пробелов) есть в `CheckContext.allowedHosts`; вычисляемый хвост допустим только после `/` хоста, остальное решает рантайм. На сервере агента список берётся только из его манифеста (`contextFromManifest`); `allowedHosts` из тела запроса `trustedInput` отбрасывает, без манифеста внешних хостов нет. Ключ бандла (`contextHash`) список не включает: уже скомпилированный бандл с литералом на убранный хост рантайм-охрана и CSP всё равно не пустят. Рецепт CSP: `img-src 'self' https://<каждый хост>`, больше ничего не расширяется; `pleatkit doctor` (находка `csp`) показывает хосты из манифеста и предупреждает, если `img-src` (или `default-src`) какой-то из них не пропускает.

### 4.3. Реестр динамических компонентов

```tsx
<PleatkitProvider config={config} store={store} userId={userId} token={...} onAuthExpired={...}>
  <Dynamic id="customer-card" props={{ customer }} />
</PleatkitProvider>
```

- Движок создаётся в `useMemo` по пользователю и конфигурации; конструктор без побочных эффектов, слушатели подключает `engine.attach()` в эффекте. Смена пользователя не размонтирует дерево хоста.
- Store недоступен или висит: через 5 с (`storeTimeoutMs`) состояние `ready`, исходная версия, `offline: true`; `refresh()` пробует снова. У `HttpStore` таймаут на каждый запрос и один повтор после 401 со свежим токеном.
- Подмена модулей: LRU-кеш из 8 вычисленных бандлов (undo/redo без повторного `import()`), `panelVersions` по панелям: перемонтируются только панели, чей код изменился.
- `ErrorBoundary` вокруг каждой панели, откат только по вине правки (B3); `rollback` проверяет head внутри очереди, две упавшие панели откатывают одну правку один раз.
- `isolated`: iframe `sandbox="allow-scripts"` со скриптом-хостом отдельным файлом (DECISIONS 16); сообщения в iframe обрабатываются по одному. `isolateEdits` в плагине отправляет в iframe каждую изменённую панель; по умолчанию выключено (тот же realm, граница это правила + CSP).

### 4.4. API рантайма

```ts
const engine = usePleatkit()
engine.draft.start(message) / write(path, source) / read / list / check() / commit(author, { requestId, bundle, expectedHeadId }) / discard()
engine.undo() / redo() / reset() / rollback(snapshotId)
engine.revertPlan(snapshotId) / revert(snapshotId)   // откат правки из середины цепочки (05 #13)
engine.previewOriginal(on)                          // «показать оригинал», head не меняется (05 #12)
engine.diagnostics()                                // id снимка, «изменено», панели, режим, offline (05 #12)
engine.agentRequest(text, extra)                    // с expectedHeadId
engine.history() / tags() / moduleStats() / refresh()
```

Браузер остаётся источником правды для файлов, сервер агента stateless по файлам:

1. Чат отправляет `POST /agent/v1/run` с файлами, `expectedHeadId` и (при указании на панель) DOM-снимком панели. По умолчанию в DOM-снимке только структура: теги, классы, test id и длины текстов; текст только при `sendDomText: true` (почта и номера маскируются), поддеревья `data-pleatkit-private` и значения полей никогда (05 #3).
2. Агент берёт контекст правил, readonly и `.d.ts` из своего манифеста (`PLEATKIT_MANIFEST`), а не из тела запроса; работает над копией файлов в памяти; `check` тот же, что в браузере.
3. Результат: `{ files, verdict: ok | partial | needs-backend | not-editable | declined | failed | clarify | refused, expectedHeadId, bundle? }`, прогресс по SSE с комментарием-heartbeat каждые 15 с. Отмена в чате обрывает запрос, сервер прерывает вызов модели.
4. Браузер коммитит только поверх того же head (`expectedHeadId`, CAS на `setHead`); при конфликте head перечитывается и правка не применяется.

## 5. `@pleatkit/agent` (Node)

- Hono: `POST /agent/v1/run` (SSE), `POST /agent/v1/compile`, `GET /agent/v1/b/:app/:file`, `POST /agent/v1/expected-cost`, `GET /agent/v1/classifier-modes`, `GET /agent/health`, плюс маршруты расширений (`AgentExtension`, ниже). Тело ограничено (16 МБ по умолчанию, 413), токен проверяется до разбора JSON.
- **Точка расширения сервера агента (решение 89, `agent/src/extension.ts`).** `createAgentApp({ extensions })` монтирует `AgentExtension { name, routes(app, ctx) }` под тем же base path, CORS и лимитом тела; `ctx` даёт провайдер, адрес и клиент store-server, `fetch`, `log`, `manifest(appId)`, `adminApp(c, body)` (то же правило админа, что у `/v1/expected-cost`), `appKey(appId)` и `reportUsage(appId, events)` (события учёта в store-server). Бинарь `pleatkit-agent` загружает модули из `PLEATKIT_AGENT_EXTENSIONS` (список или `none`); без переменной берёт `@pleatkit/agent-cloud`, только если `package.json` развёртывания объявляет его зависимостью (как стор, `src/extensions-loader.ts`). Для вызовов вне цикла правки у провайдера есть общий `completeJson({ name, instructions, message, schema, maxTokens, scripted? })` на модели классификатора (`ModelProvider.classifierModel`): structured output у Anthropic, JSON mode у OpenAI-совместимых; у `scripted` ответ даёт функция `scripted(fixtures)` самого вызова, recording пишет строку `kind: 'json'`, replay её возвращает. Открытый агент сам таких вызовов не делает и промптов облака не содержит: карта хотелок, недельный дайджест и массовый перенос правок в новый релиз живут в приватном `@pleatkit/agent-cloud` (маршрут `POST /agent/v1/wishes`, бинарь `pleatkit-ops digest|carry-over`).
- Этап 4c, блок 3. Компиляция бандла (`BundleService.compile`) отвечает «скомпилировано» только после того, как бандл записан в store-server: запись в кеш процесса после записи в стор, параллельные компиляции одного ключа ждут одну запись, неудачная запись не кешируется (решение 70.8).
- Этап 5, блок 2 (решение 73). **Классификатор параллельно основной модели** (73.3): `runAgent` отправляет запрос классификатора, сразу стартует сессию основной модели и её первый вызов (`classifierMode: parallel`; `sequential` возвращает старый порядок; с блока 4 режим по умолчанию выбирается для каждого приложения автоматически, см. ниже); ответ классификатора решает: `ui` (и `needs-backend` с `screen_part`) — первый ход уже идёт и используется, `needs-backend`, вопрос, `off-topic` или `adversarial` — первый вызов отменяется (`AbortController`), его токены API не сообщает. `timings.overlapMs` — сколько первый вызов шёл, пока классификатор думал. На ответах классификатора `needs-backend` администратор получает `backendNote` из gist, метки и фразы пользователю (73.4). Промпт 5c: классификатор видит контракт данных приложения (`dataContracts.digest`) вместо одних файлов api/types/models, про `meta` говорит только если оно есть, помечает вывод данных наружу и обманные элементы как `adversarial` (не `ui` → `declined`) и отдаёт `screen_part` (смешанный запрос идёт к основной модели за `partial`).
- Манифест (этап 5, блок 2): дайджест дизайн-системы показывает пропсы компонентов и их варианты (таблицы `cva()` через `VariantProps<typeof x>`, локальные union-типы, `export { A }` и `export default A`, 73.7); `coreTypes` несут ambient-объявления приложения (`src/**/*.d.ts` с `declare module`/`declare global`: аугментации TanStack Table, `*.svg?react`); контракт данных берёт все файлы `readonly/` (кроме компонентов дизайн-системы) и раскрывает то, что они реэкспортируют или импортируют из core, из `.d.ts` (типы zod и иконок сокращаются). Проверка типов агента отклоняет правку только за ошибки, которых нет в файлах релиза (`input.base`), и берёт ambient-объявления корнями программы. Статическое правило `no-computed-url` не проверяет проп `data` у компонентов (`<BarChart data>`), только у элементов.
- Этап 5, блок 3 (решение 74). **Ранний вызов стримится** (74.1): первый вызов основной модели, стартующий вместе с классификатором, идёт через `messages.stream` (`TurnOptions.stream`), инструменты те же (без `eager_input_streaming`, если не `PLEATKIT_STREAM=1`), так что кешируемый префикс один для стримленных и обычных вызовов. Отмена закрывает поток и останавливает генерацию; что поток успел сообщить (`message_start`: вход и кеш; выход по увиденным дельтам, размышление не видно) попадает в `usage` и `cancelledCall` результата (`started: false`, если отмена раньше `message_start`: тогда API не сообщает ничего, а префилл, судя по записи кеша, всё равно выполнен). **typecheck в цикле по умолчанию** (74.2, как 63.4): `typecheckFromEnv` включает его, когда найдена папка приложения с `node_modules` (`PLEATKIT_TYPECHECK_ROOT` или папка над `dist/` манифеста; для `PLEATKIT_MANIFESTS` своя у каждого приложения по `context.namespace`); `0` выключает, `1` включает и для серверной компиляции коммитов (`commitTypecheck`, как раньше). Проверяются только изменённые файлы и динамические файлы, которые их импортируют (`affectedFiles`), ошибки релиза отбрасываются; файлы релиза теперь доходят до рабочей области всегда, а не только при защищённых элементах (без них каждая правка shadcn-admin отклонялась бы за `CheckedState` самих панелей релиза). Цена: тёплая проверка shadcn-admin ≈ 1,2–1,6 с (его типы TanStack и Recharts), TailAdmin ≈ 0,1–0,3 с, первая в процессе ≈ 5 с. **Модель под лимитами** (`rate-limit.ts`): каждый вызов модели в цикле (классификатор, ранний и обычные ходы) идёт через общий для процесса FIFO-семафор `modelGate` (`PLEATKIT_MODEL_CONCURRENCY`, 8) и `callModel`: 429, 529 и `overloaded_error` повторяются после `retry-after` (иначе 1, 2, 4 с с разбросом) не больше `PLEATKIT_RATE_LIMIT_RETRIES` (3) раз с шагом «The AI service is busy, retrying» в SSE; 408, 409, 5xx и обрыв соединения повторяются так же, молча; повтор, который не успел бы до дедлайна прогона, не начинается. Не помогло — вердикт `failed`, `rateLimited: true`, `stopReason: 'rate-limited'`, событие `edit.rate_limited` (экран Plan в /admin считает их по дням). Собственные повторы SDK выключены (`maxRetries: 0`), кроме карты хотелок; провайдеры откатывают историю диалога при неудачном вызове, чтобы ход можно было повторить. Классификатор (промпт 5f): инструкции и контекст приложения в системном промпте под точкой кеша, в сообщении пользователя только запрос (кеш классификатора 0 % → 74 % входа).
- **Подрезанный контекст агента** (74.6, `vite-plugin/src/context.ts`): плагин строит `manifest.agentContext` — `.d.ts` модулей readonly и core-типов, достижимых из импортов файлов релиза: имена идут через баррели (`export { X } from './x'` только для X, который нужен), модуль, чьи собственные экспорты используются, тянет то, что импортируют его объявления (а не исходник: `cn` в теле компонента не попадает), строки импорта ассетов (`*.svg?react`) убираются. Предел `agentContext.capTokens` (12 000 оценочных токенов по умолчанию, `pleatkit({ agentContext: false })` выключает): сверх него отбрасываются самые дальние модули, их список в промпте как «read_file при нужде»; сборка печатает размер. Промпт (`digestsFromManifest` → `PromptDigests.context`) показывает `<readonly_context>` вместо `<readonly_sources>` и `<core_types>`; `read_file`, проверки и typecheck по-прежнему видят все исходники. Дайджест дизайн-системы подробно описывает только достижимые компоненты, остальные одной строкой «Also available» с путями. Браузерная копия манифеста `agentContext` не несёт. Префикс по `count_tokens`: shadcn-admin 33 819 → 13 086, TailAdmin 12 767 → 6 048, демо 7 727 → 6 218.
- Этап 5, блок 4 (решения 75 Р5, 76.3). **Авто-выбор parallel/sequential** (`classifier-mode.ts`): `PLEATKIT_CLASSIFIER=auto` по умолчанию (`parallel` и `sequential` фиксируют режим для всех приложений, как раньше; раннер по-прежнему получает только `parallel` или `sequential`, эвалы передают его явно). Сервер (`ClassifierModes`) держит для каждого приложения скользящее окно 7 дней почасовыми корзинами (не больше 169 корзин на приложение, не больше 1000 приложений, давно не виденные вытесняются): сколько запросов прошли через классификатор (`timings.classifyMs` задан: не указанная панель, не ответ на уточнение, не миграция) и сколько из них классификатор ответил сам (вердикт `needs-backend`, `clarify`, `refused` или `declined`, ноль вызовов основной модели и пустой лог инструментов — пути `cancelEarly()` в `loop.ts`). Меньше 20 таких запросов в окне — `parallel`; иначе доля > 50 % включает `sequential`, а обратно в `parallel` приложение возвращается при доле ≤ 45 %. Полоса нужна только против шума: при выборке 20 один запрос сдвигает долю на 5 пунктов, а сама доля от режима не зависит (классификатор отвечает одинаково в обоих режимах). Первый запрос приложения в процессе ждёт историю из store-server (`GET /v1/classifier-stats?sinceMs=`, агент или админ: те же почасовые корзины, посчитанные SQL по журналу запросов — `timings.classifyMs`, вердикт, `json_array_length(log) = 0`, поэтому годятся и старые строки, нового поля не нужно; таймаут 3 с, без store-server или при ошибке — только память процесса). Режим виден: `timings.classifierMode` в результате и в журнале запросов (когда классификатор работал), строка лога `<app>: classifier parallel -> sequential (…)` на каждом переключении, `GET /agent/v1/health` → `classifier: { setting, apps: { <app>: { mode, classified, alone, share, seeded } } }`. Несколько процессов агента считают каждый своё поверх общей истории на момент первого запроса.
- Этап 5, блок 4 (решения 76.1, 75 Р3 и пункт координатора). **Хвост в кеш со второго вызова** (`AnthropicProviderOptions.cacheTail`, `PLEATKIT_CACHE_TAIL`, по умолчанию `after-first`): первый вызов правки несёт только точку кеша на системном блоке, хвост запроса (динамические файлы) уходит обычным входом ($2/M вместо записи $2,5/M), со второго вызова добавляется автоматическая точка на хвосте. Замер на shadcn-admin (по 5 разных задач на режим, чтобы режимы не грели хвост друг другу): правка в один вызов $0,026–0,031 против $0,0365, запрос, на который ответил один классификатор, $0,0001 против $0,0285 (отменённый ранний вызов больше не пишет хвост), правка в два вызова дороже ($0,063 против ≈ $0,038). `always` возвращает старое поведение. **`backendQuote`** (`AgentResult`, `protocol.ts`): на `partial` и `needs-backend` дословная часть запроса, которой нужен сервер, чтобы шторка показала «Sent to your admin: "…"»; основная модель отдаёт её полем `backend_quote` в `finish`, классификатор на собственных ответах `needs-backend` — полем `backend_quote` своей схемы; `backendQuoteOf` проверяет, что цитата — подстрока запроса (пробелы нормализуются, хвостовая пунктуация отбрасывается), иначе подставляет весь запрос. Промпт 5g → 5h (формулировка 5g тянула смешанные запросы в `needs-backend`, 5h ставит цитату после метки). В журнал запросов store-server поле пока не пишется (колонки нет); шторка получает его в SSE-результате.
- `pleatkit doctor` (этап 5, блок 2): проверка `release` гоняет `check` агента по файлам релиза (панель релиза, которую check отклоняет, ломает каждую правку); `context-budget` при `PLEATKIT_API_KEY` считает префикс и хвост через `count_tokens` API (бесплатно, `countPromptTokens` в агенте, тот же промпт, что у сервера), без ключа оценивает (2,2 символа на токен кода, инструкции и инструменты 3 500, откалибровано по счётчику, 73.5).
- **Ожидаемая цена правки** (этап 5, блок 4, решение 75 Р2; `agent/src/expected-cost.ts`). `expectedEditCost({ prefixTokens, tailTokens }, model, classifierModel)` по таблице цен (`MODEL_PRICES` теперь в `@pleatkit/runtime/compiler`, `runtime/src/pricing.ts`; агент реэкспортирует `priceOf`/`costUsd`): первый вызов = префикс из кеша (0,1× входа) + хвост обычным входом (с блока 4 первый вызов не пишет хвост в кеш, `cacheTail: 'after-first'`, решение 76.1; `tailWrite: true` считает старое поведение с записью 1,25×) + 550 выходных токенов; второй вызов в 25 % правок = (префикс + хвост) из кеша + 700 токенов записи (первый ход) + 200 выходных; плюс классификатор Haiku (2 000 токенов фиксированной части из кеша, 40 входа, 90 выхода, ≈ $0,00007). Холодная правка (первая после 5 минут простоя): префикс и фиксированная часть классификатора пишутся, а не читаются. Константы откалиброваны по 90 применённым правкам живых серий (apps-5f, probe-5f, live-5d, live-5d-sequential): медиана выхода правок в один вызов 475–597, доля правок в два вызова 20 из 90. Сверка с `count_tokens` (промпт 5f, Sonnet 5.5): демо 6 218 + 1 793 → $0,0126 (холодная $0,0272) против медианы $0,0128 серии probe-5f и $0,0094–0,0113 серий live (тогда хвост не писался в кеш; с `tailWrite: false` модель даёт $0,0117); shadcn-admin 13 086 + 10 266 → $0,0360 ($0,0663) против $0,0352 первых попыток apps-5f; TailAdmin 6 048 + 7 994 → $0,0284 ($0,0426) против $0,0287. Холодный прогон shadcn-admin в probe-5f стоил $0,0626. Модель без цены (OpenAI-совместимые) даёт `null` и список `unpriced`. `pleatkit doctor` печатает в `context-budget` «Expected cost per edit on this app: $X (cold: $Y) with <модель> and the <классификатор> classifier» по подсчитанному или оценённому размеру (`PLEATKIT_MODEL`, `PLEATKIT_CLASSIFIER_MODEL`, `PLEATKIT_PROVIDER`). Сервер агента: `POST /agent/v1/expected-cost { appId }` (токен админа, в разработке заголовок админа) считает по манифесту приложения через `count_tokens` провайдера (`ModelProvider.countPromptTokens`, есть у `AnthropicProvider`; кеш в памяти по хешу релиза и модели), иначе оценкой `estimatePromptTokens` (2,5 символа на токен всего промпта: по счётчику 2,46–2,62 у префикса и 2,45–2,59 у хвоста на трёх приложениях) и отвечает `source: counted | estimated`; `scripted` оценивается по моделям по умолчанию с пояснением в `note`.

- Этап 5, блок 5. **Метка `restore`** (решение 82.2): пятая метка классификатора (схема `CLASSIFY_SCHEMA`, промпт 5i) для «верни как было» без новой правки; `runAgent` отменяет ранний вызов и отвечает вердиктом `restore` без модели (статус журнала `clarifying`, счётчик авто-режима считает его ответом одного классификатора); шторка по нему открывает историю версий. **Тёплый typecheck** (брейн-шторм 17 §4, `typecheck.ts`): разрешения модулей на диске (граф `.d.ts` пакетов) кешируются на всё время жизни проверяющего, каждая программа строится из предыдущей (`oldProgram`); сервер при старте прогревает проверку каждого приложения с манифестом (`warmTypecheckApps`, `PLEATKIT_TYPECHECK_WARM=0` выключает и кеш, и прогрев). shadcn-admin: проверка правки 1,1 с медиана / 4 с максимум → 0,18 / 0,6 с. **Доли авто-режима по приложениям** ушли из `/agent/v1/health` (без авторизации там только их число) в `GET /agent/v1/classifier-modes` (токен админа видит своё приложение, в разработке заголовок `x-pleatkit-admin: 1` все). - Этап 5, блок 6 (решения 83, 84). **Ансамбль классификатора** (`classifier-ensemble.ts`, `providers/typesafe.ts`; `PLEATKIT_CLASSIFIER_ENSEMBLE=jev` и `TYPESAFE_API_KEY`, по умолчанию выключен, `DEFAULT_CLASSIFIER_ENSEMBLE`): `providerFromEnv` оборачивает провайдера модели (не `scripted`) в `EnsembleProvider`, всё кроме `classify` идёт во внутреннего. `classify` стартует вместе Jev (TypeSafe System One, `POST https://api.typesafe.ai/v1/systemone`, `Authorization: Bearer`, `model: jev-latest`; один вызов, два вопроса: `route` типа `choice` с восемью маршрутами и формулировками пробы `jev-compare.mjs` и `adversarial` типа `noul` «запрос обманный, вредный или отправляет данные наружу?»; `state` = фраза о приложении, `classifierContext` (панели и контракт данных) и запрос; таймаут 3 с) и классификатор модели (Haiku), оба вместе с ранним вызовом основной модели, как раньше. Jev решает сам (`jevDecides`), если маршрут `ui`, `partial`, `needs-backend` или `restore`, уверенность ≥ 0,9, `noul` < 0,2 и Haiku, если уже ответила, не пометила запрос `adversarial`; `partial` → метка `ui` (экранную часть делает основная модель, она же пишет `backendQuote`). Иначе решает Haiku, как без ансамбля; Jev, не ответивший за 150 мс после Haiku, не ждём. `needs-backend` от Jev берёт фразу пользователю, gist и `backendQuote` у Haiku: её ответ, если тоже `needs-backend`, иначе вызов `quoteBackend` (Haiku, только эти поля). Ответ Haiku после решения Jev приходит в `ClassifyInput.onLate`: прогон учитывает его расход и метку намерения, пока идёт. `Classification.extraUsage` (Jev, догоняющие вызовы) идёт в `usage` прогона; `AgentResult.classifier = { decidedBy: 'jev' | 'model', jev: { route, confidence, adversarial, ms } }`. Цена Jev в таблице рантайма (`jev-latest` и `jev-<версия>`: $0,042 за 1M входа, выход бесплатно). Замер блока 6: точность как у Haiku (304 и 305 из 318), решение маршрута 1,37 → 1,10 с медиана (Jev сам на 46 % запросов за 0,3 с), классификатор $0,000085 → $0,000133 на запрос; в параллельном режиме задержку правки задаёт основная модель, поэтому по умолчанию выключен (`evals/REPORT-2026-10-19-block6.md`).
- **Хвост = указанная панель** (решение 84.5, промпт 5j; `tailOf`/`pointedFiles` в `prompt.ts`, `RunOptions.tail`, `PLEATKIT_TAIL=pointed|all`, по умолчанию `pointed`): когда пользователь указал панель (`target`), первое сообщение несёт файл панели и все динамические файлы, которые он импортирует относительными путями (транзитивно, CSS и CSS-модули тоже), остальные файлы зоны перечислены строками «путь (N строк; exports …)» (`exportsOf`), их показывает `read_file`. Без указанной панели, при миграции и откате правки — все файлы, как раньше. shadcn-admin, зона 7 файлов: некэшированный вход вызова 10 350 → 920 токенов, правка $0,030 → $0,012 медиана.
- **Скриншот указанной панели** (брейн-шторм 17 §14, `AgentRunRequest.targetImage`): снимок панели «до» идёт модели последним изображением после картинок пользователя с одной фразой (промпт 5j), в тех же лимитах изображений (`validateRequest`). A/B блока 6 (оценка судьи 4,2 → 4,0) прироста не дал: шторка его не шлёт, поле оставлено.
- **TTL кеша системного префикса** (брейн-шторм 17 §21, `AnthropicProviderOptions.cacheTtl`, `PLEATKIT_CACHE_TTL=1h|5m`, по умолчанию `1h`): точка кеша на системном блоке пишется с `ttl: '1h'` (запись 2× входа вместо 1,25×), хвост остаётся 5-минутным (более длинный TTL идёт первым, как требует API). `usageOf` читает `cache_creation.ephemeral_1h_input_tokens` в `TokenUsage.cacheWrite1hTokens`, `costUsd` доплачивает за них (2× − 1,25×) входа; `expectedEditCost` считает холодную правку с записью на час (`prefixTtl`).
- **Еженедельная проверка дрейфа** (брейн-шторм 17 §20, `evals/src/weekly.ts`, `pnpm eval:weekly`, шаблон `docs/release/weekly.yml`): реплеи всех наборов с baseline и слепых наборов, затем 14 задач демо × 1 вживую; при регрессии набора или живом прогоне ниже baseline на 2 задачи и больше — алерт `eval-drift` через тот же канал, что у сервера агента (`sendAlert` в `alerts.ts`: вебхук и e-mail).
- `pleatkit doctor` (этап 5, блок 5): находка `zone-size` по кривой цены от размера зоны (каждая правка шлёт все файлы зоны: $0,0085 + $0,026 за 1000 строк на Sonnet 5.5, замер на shadcn-admin), предупреждение больше 450 строк зоны или 300 строк одной панели; `externals` считает записи и модули отдельно и предупреждает о записи `/*`, под которую не подходит ни один модуль. `pleatkit init --suggest` (`cli/src/suggest.ts`): по графу импортов (парсер TypeScript, приложение не запускается) предлагает панели, их файлы-помощники, места рендера с пропсами, readonly-модули реэкспорта, externals и блок плагина; `--write` создаёт только модули реэкспорта.
- Инструменты (строгие схемы): `list_files`, `read_file`, `write_file`, `check`, `finish`. Результаты инструментов не длиннее 24 000 символов, ошибки дедуплицируются, не больше 10.
- `max_tokens` одного вызова = остаток видимого бюджета правки + 8k на размышление (не больше 16k). Ответ, обрезанный по `max_tokens`, не исполняет последний вызов инструмента: модель получает об этом результат.
- Лимиты из конфигурации (по умолчанию 12 вызовов, 90 с, 8k видимых токенов, $ на правку по тарифу); текст промпта берёт их оттуда же.
- В production сервер не стартует без ключа приложения, секрета JWT и `PLEATKIT_MANIFEST`.

## 6. `@pleatkit/store-server` и дашборд

**Открытое ядро и облако (решения 70.1, 89).** Self-host: открытый стор (`@pleatkit/store-server`, MIT, публикуется). Облако: то же ядро плюс приватные пакеты расширения `@pleatkit/store-cloud`, `@pleatkit/agent-cloud` и `@pleatkit/admin-cloud` (в приватном репозитории pleatkit-cloud, здесь их нет). Открыто то, что нужно, чтобы поставить и доверять: снимки, головы, бандлы, журнал запросов с approve/reject/rollback, разметка запросов, квоты и лимиты приложения (`app_plans` как данные квот, F14), события (учёт), цепочка аудита, роли `user` и `admin`, флаги и kill switch, экспорт, удаление, хранение L0 (`applyRetention`: текст 90 дней, журнал 30). Облако добавляет: отчёт о пилоте (`GET /v1/report` с денежными колонками), карту хотелок (`/v1/admin/wish-items`, `/v1/admin/wishes`, таблица `wish_maps`), прогоны переноса правок в новый релиз и их откат (`/v1/admin/releases*`, таблицы `releases` и `release_items`), поиск по коду версий и откат по выборке (`/v1/admin/snapshots?grep`, `POST /v1/admin/snapshots/rollback`), роль `support` и «глазами пользователя» (`x-pleatkit-act-as`), слой обучения (`request_facts`, `app_salts`, `learning_settings`, `PUT /v1/admin/learning`). В открытом сторе эти маршруты отвечают 404; таблицы баз 0.3 остаются на месте, но открытое ядро их не создаёт и при удалении не трогает.

Точка расширения (`src/extension.ts`): `StoreExtension { name, ddl, migrate, routes(api, ctx), middleware(api, ctx), roles, actAs(who, target), adminAccess(who, method, path), jobs, onRequestLogged, onOutcome, erase, count, settings }`; `ctx` даёт `db`, `audited`, `place`, `event`, `outcome`, `setHead`. `createStoreApp(db, { extensions })` создаёт таблицы расширений, ставит их `middleware` сразу после определения вызывающего и монтирует их маршруты за той же авторизацией, лимитом тела, идемпотентностью и правилом «/admin только admin» (чтение другой роли открывает `adminAccess` расширения). Роль, кроме `user` и `admin`, и заголовок `x-pleatkit-act-as` без расширения, которое их объявляет (`roles`, `actAs`), получают 403 `{ code: 'cloud-feature' }`. `runMaintenance` (ежечасно в бинаре) делает `edit.alive24h`, хранение L0 и задачи расширений. Бинарь `pleatkit-store` загружает модули из `PLEATKIT_STORE_EXTENSIONS` (список или `none`); без переменной берёт `@pleatkit/store-cloud`, только если `package.json` рабочей папки (развёртывания) объявляет его зависимостью: в воркспейсе пакет может резолвиться и без этого (скрытый hoisting pnpm, `NODE_PATH`), и открытый стор не должен подхватить облако случайно. У открытого пакета нет зависимости от закрытого. Демо и `examples/t1-vite` работают на открытом ядре: пакета облака у них нет.

**Удаление (решение 70.2).** `DELETE /v1/admin/users/:id` и `DELETE /v1/admin/apps/:id` (только admin; user получает 403, вызов «от имени» 400). Без `?confirm=` (или с устаревшим) ничего не удаляется: 409 со счётчиками и токеном; токен это хеш субъекта и счётчиков, так что он меняется, когда меняются данные. С токеном в одной транзакции удаляются снимки, головы, запросы, события (учёт), бандлы пользователя и подписанные бандлы его файлов (по `filesHash` подписи; корневой снимок общий и не трогается), записи прогонов, ответы идемпотентности, корзины квот `user:<id>:*`, флаги пользователя, метки запросов и строки расширений (в облаке: факты, строки переноса, ссылки в картах хотелок; их счётчики идут с префиксом имени расширения, например `releases:release_items`). Для приложения то же по всем таблицам `app_id`, включая цепочку аудита, план и настройки. В цепочку дописывается надгробие `erase.user` / `erase.app` со счётчиками и случайным id `erased:<16 hex>` без персональных данных. `events` и `audit` остаются append-only: триггер DELETE пропускает удаление только при строке-метке в таблице `erasing`, которую удаление вставляет и убирает в своей же транзакции (аудит удаляется только при удалении приложения). Удаление пользователя цепочку аудита не трогает: её строки связаны хешами, в них id пользователя остаются (открытый вопрос DEVLOG). CLI: `pleatkit erase`.

- Hono + Drizzle, SQLite. Таблицы: `snapshots` (PK `(app_id, id)`, insert-only: триггер запрещает UPDATE всего, кроме однократной привязки `request_id`), `heads`, `requests`, `bundle_files` (ключ, владелец, подпись; публичные только подписанные агентом), `events` и `audit` (append-only), `flags`, `idempotency`, `quota_buckets`, `app_plans`, `app_settings`, `request_labels` (разметка, решение 81). Старая таблица `bundles` не используется.
- Эндпоинты под `/v1/`: снимки и головы (`POST /snapshots/:id/head` с `expectedHeadId` это CAS, 409 `head-conflict`), бандлы, запросы, квоты, события, флаги, админ (`/admin/requests` сортирует в SQL и считает `isHead` одним join), аудит, экспорт.
- Авторизация: ключ приложения (сервер→сервер), JWT пользователя, демо-заголовки только вне production. Тело запроса ограничено (4 МБ по умолчанию, 413) и читается после авторизации.
- Роли (C8): `user` и `admin` в JWT (`admin` может всё под `/admin`). Другая роль (например `support` облака) и заголовок `x-pleatkit-act-as` без расширения стора получают 403 `cloud-feature`. В облаке `support` читает `/admin` (кроме экспорта) и смотрит версию пользователя «от его имени»; каждый такой вызов пишется в цепочку аудита с обоими id, писать от имени пользователя может только `admin` (решение 70.5). `HttpStore` передаёт такие заголовки через `headers`.
- **Разметка и `backendQuote`** (этап 5, блок 5; решения 81, 82.5; `store-server/src/labels.ts`). Колонка `requests.backend_quote`: дословные слова запроса, которым нужен сервер (из результата агента, строка до 1000 символов; хранение L0 стирает её вместе с текстом). Таблица `request_labels` (PK `(app_id, request_id, labeler)`: одна текущая метка на запрос и разметчика, повторное нажатие заменяет; `labeler` это id админа из авторизации, `admin` для ключа приложения). Метки (семь кнопок, клавиши 1–7): `ui`, `needs-backend`, `clarify`, `off-topic`, `declined`, `mixed`, `restore` (решение 84.2). Предложение классификатора не хранится, а выводится из строки журнала: вердикт `restore` → `restore` (и без `classification`); нет `classification` → нет предложения; `intent_label = adversarial` → `declined`; `ui` с вердиктом `partial` → `mixed`; `unclear` → `clarify`; `needs-backend`, `off-topic`, `ui`, `restore` по имени; другие метки → нет. Расхождение: метка человека не равна предложению. `GET /v1/admin/labels?filter=unlabelled|all|disagreements&limit&cursor&since` (новые первыми, курсор `<ms>:<rowid>`, счётчики разметчика и его последние метки), `POST /v1/admin/labels { requestId, label }` (`label: null` снимает метку; только admin), `GET /v1/admin/labels/export?filter=disagreements|all` (метки всех разметчиков с текстом запроса). `pleatkit labels export` пишет их пробами для `pnpm eval:classify -- --probes` (`clarify` → `unclear`, `declined` → намерение `adversarial`, `mixed` → `ui`, `restore` по имени; `evals/src/probe-labels.ts`). Экспорт приложения и удаление включают метки.
- Дашборд `/admin` в demo-crm: разделы `?view=` requests (таблица запросов, diff, журнал инструментов, откат, отклонение, «взять в работу»; под ответом агента цитата `backendQuote`), labels, flags, events, audit, plan (лимиты, расход, ожидаемая цена правки). Экраны облака (Wishes, Releases, поиск по коду с откатом по выборке, ссылка «глазами пользователя», деньги отчёта) лежат в приватном `@pleatkit/admin-cloud`.

## 9. Тесты и критерии готовности

- Vitest: VirtualFS, hash снимка, цепочка undo/redo, запрет записи вне dynamic, парсинг ошибок esbuild.
- Playwright headless (`--headless`, никаких окон): четыре сценария выше со `scripted` провайдером; проверка, что у `bob` карточка не изменилась после правки `alice`.
- Эвал-харнесс (`evals/`, `docs/evals.md`): задачи `evals/tasks/*.json` (демо, публичные) и `evals/tasks/apps/*.json` (приватные эвалы, `PLEATKIT_PRIVATE_EVALS`) (35 задач на двух чужих приложениях в `evals/apps`, решение 73.1) гоняются через тот же `runAgent` в процессе, с доверенным входом из манифеста сборки своего приложения, как у `POST /agent/v1/run`; браузерный оценщик поднимает сборку нужного приложения (`EVAL_APP`), панели чужих приложений находит по `data-pleatkit-id`, проверки по структуре и тексту (`selector`, `role`, `matches`, `click`, `maxHeight`, `css`); оценщики: вердикт, изменение, общий `check`, `tsc` (корень с `node_modules` приложения), текстовые инварианты, предикаты, бюджет и Playwright (результат коммитится в собранное демо через `draft.commit('agent')` под `?eval=1`, проверяются отсутствие баннера падения, testid полей по соглашению демо (`apps/demo-crm/docs/design-system.md`: поля данных держат `data-testid` = имя поля; документ попадает в кешируемый префикс как `designSystem.docs`) и текст/классы того, что видит пользователь). `pnpm eval:sanity` (эталоны проходят, нулевой агент проваливает задачи с изменением), `eval:replay` (транскрипты `ReplayProvider`: scripted против `evals/baseline.scripted.json`, `--set live` — три попытки на задачу живой серии против `evals/baseline.json`), `eval:pin`, `eval:report` (с попытками: задачи по попыткам, задержка медиана/p90, цена правки, `cacheHitRate()`). Живая запись: `eval:record -- --live [--set] [--trials] [--no-classifier]`, результаты записи с реальными задержками лежат в `evals/recordings/<set>/record.json`. Изменение промпта или модели идёт с этим отчётом (решения 43, 63).
- Метрики, которые печатает e2e: время от запроса до перерисовки, размер и время инициализации esbuild-wasm.
- Готово, когда: `pnpm install && pnpm build && pnpm test && pnpm e2e` проходят на чистой машине; `pnpm dev` поднимает demo-crm + agent + store-server одной командой; README объясняет установку в чужой Vite-проект за 5 шагов.

## 10. Что сознательно не делаем в демо

Next.js и webpack, настоящая авторизация, многопользовательские общие правки, мерж правок при обновлении базового снимка (при изменении `dynamic` в новом релизе приложения пользовательский снимок просто помечается `stale`, и в UI предлагается «сбросить» или «попросить агента перенести»), десктоп/Tauri, проверка типов в браузере (только на сервере агента через `tsc --noEmit` по желанию, флаг `typecheck: true`).
